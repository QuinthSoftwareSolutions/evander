# Add an editable progress image to a Teams message


This ExecPlan is a living document. Maintain `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` as implementation proceeds, following `templates/PLANS.md`. Repository paths below are relative to the worktree root.

## Purpose / Big Picture


A documentation job should be able to post one progress message when writing starts, then change its graphic and readable status as sections finish and review and export advance. Readers should see completed chapters and completed sections without receiving a new reply for every update. The picture is generated by ordinary code from verified job state; updating it requires no additional model inference.

Extend the session-owned Teams posting and editing implementation already on `feature/teams-message-edit`. Use a new immutable PNG URL for each changed graphic and replace only the explicitly designated image region in the same message body. Keep other mentions, attachments, hosted images, cards, file links, and their surrounding layout intact.

Local implementation was authorized on 20 October 2026, in the same isolated worktree and branch. A subsequent instruction authorized committing, pushing and an agent review against the branch's merge base. Live consent, live Graph tests, deployment, operator workflow changes and PR creation remain outside that authorization. Production documentation sessions and configuration remain untouched. Channel/client compatibility and a later operator rollout remain release gates after review and CI/CD.

## Surprises & Discoveries


The ordinary delegated message PATCH endpoint accepts a request containing a body and a `hostedContents` collection with HTTP 204, but this was not a successful image replacement in the live probe. Readback normalized the temporary reference to `about:///hostedContents/2/$value`, listing hosted content returned an empty collection, and the old hosted image endpoint returned 404. A direct POST to an existing message's `hostedContents` relationship returned 405. A collection-only PATCH returned 400 because body content was missing; that error alone does not establish whether all possible collection updates are unsupported.

Changing the message body's image source to an already valid image reference did persist. More usefully for a solution without extra image-carrier posts, changing the same message to signed external PNG version A and then version B returned 204 each time. GET preserved the same message ID and the respective source URL; unauthenticated requests to those exact signed sources returned HTTP 200, image/png, and bytes matching the intended different SHA-256 hashes. This establishes API-level reference replacement in a chat. It does not establish channel permissions or Teams desktop/mobile rendering.

The existing account's token includes `Chat.ReadWrite`, `ChannelMessage.Read.All`, and `ChannelMessage.Send`, but lacks `ChannelMessage.ReadWrite`. No scopes, identities, session grants, or tenant policies were changed for the probe. A private one-member group chat was usable; creating a one-member one-to-one chat was rejected. Production code should continue to accept configured existing targets and must not create chats while resolving edit targets.

The public artifact route already serves immutable staged artifacts using signed URLs. Its URL lifetime is bounded by both link TTL and artifact expiry, and its response uses `Cache-Control: no-store`. It currently uses download-style Content-Disposition; the signed-in client proof must check whether a narrow image response adjustment is necessary. Do not infer a Microsoft image-cache duration or assume that reusing a URL will refresh pixels.

Pillow is already a core dependency in `pyproject.toml`. A small PNG chart can therefore be generated without adding Chromium, a browser service, JavaScript packages, or model calls. Browser automation remains relevant for client acceptance, not for drawing the progress bar.

Implementation discoveries (20 October 2026): A rich message suffix can close a wrapper opened in the text prefix, so image-slot discovery must parse the complete acknowledged HTML before calculating suffix-relative spans. The mocked rich-content cases now cover this. A lost PATCH acknowledgment can outlive its signed source; notification recovery first reconciles the original body without republishing that expired source, then renews retained verified pixels. Cross-process creation/edit tests and fixed-clock expiry tests cover these cases. The event-schedule effect is a core-executed registry placeholder, so the generic coordinator uses its existing ScheduledInternalEventStore through the shared metadata-aware builder, with no new daemon or model wake.

Merge-base review discoveries (20 October 2026): selecting a source verifier from pre-lock edit state allowed a waiting text-only call to commit a corrupt pending image. Every command now supplies a lazy verifier, and the service invokes it using locked state. Hardcoding the default orchestration database left timers unpolled with custom storage; the effect now forwards runtime metadata to the shared store builder, including the trigger wake path. Object-form `$ref` dictionaries were accepted as generic configuration but never resolved by the runtime. The examples now use `${{node_id.output}}` strings and are tested through the real resolver and providers, including flush/renew event payloads and terminal image clearing. The example instructions also use the actual `trigger:event` type.

## Decision Log


Decision: Use immutable externally served PNG versions, replacing an image source in the body, rather than PATCHing image bytes or overwriting a stable URL. Rationale: The live probe verified the former at the API boundary and demonstrated a false success for the tested hosted-content upload. Distinct references also avoid relying on client cache invalidation. Date/Author: 2026-10-19 / Codex.

Decision: Make only one explicitly selected image region editable. Rationale: Existing text-edit authority promises to preserve rich content. A new image parameter must not allow callers to replace arbitrary screenshots, files, cards, mention collections, or HTML. Existing receipts acquire no new image authority. Date/Author: 2026-10-19 / Codex.

Decision: Extend `teams_update_message` and `effect:teams:update-message` additively, and factor file-post authorization into the same command service for a real-session posting effect. Rationale: Agent calls and deterministic workflows need identical ownership, file-send, approval, directory, and audit behavior; the anonymous host workflow sender is unsuitable for editable session-owned progress. Date/Author: 2026-10-19 / Codex.

Decision: Separate generic media primitives and a generic progress renderer from operator documentation wiring. Rationale: Customer repositories, identities, current jobs, approved outlines, and live pack files belong in operator-owned storage. Ship a synthetic example; use revision-gated Admin APIs for any later operator pack change. Date/Author: 2026-10-19 / Codex.

Decision: Keep all current documentation jobs on their existing behavior. Rationale: Their messages were not posted with image-edit receipts, and their running generations must not be interrupted, re-prompted, or silently migrated. Date/Author: 2026-10-19 / Codex.

Decision: Treat client rendering and channel operation as outstanding release gates. Rationale: A retained img URL and a successful source download do not prove that a Teams client displays or refreshes it, and the current token cannot verify channel edits. Do not expand permissions automatically or claim channel readiness from the chat probe. Date/Author: 2026-10-19 / Codex.

Decision: Schedule an expiry-aware image renewal even when visible progress is unchanged. Rationale: Section and phase events may stop during a long review or blocker, while every signed source still expires. Renewal must deliberately change the source version and preserve ordinary identical-retry no-ops. Date/Author: 2026-10-19 / Codex, following independent review.

Decision (2026-10-20): Add effect:teams:sync-progress-message as a generic optional add-on coordinator, alongside the planned rendering and file-post primitives. Rationale: durable sequencing, coalescing, source renewal and notification-only retry should have one tested implementation rather than be rebuilt separately in each operator pack. It defaults disabled and contributes no production workflow.

Decision (2026-10-20): Serve only server-generated progress PNG artifacts inline through the existing signed route, after signature/expiry checks and a PNG signature check; retain attachment disposition for other files and set nosniff. This supplies the local embedding path while authenticated Teams-client rendering remains an unverified release gate.

Decision (2026-10-20): Keep source verification lazy but always available to the serialized edit service, and construct progress timers from trusted effect runtime metadata using the core scheduled-store builder. Validate example bindings by executing the resolved fragment chain rather than treating materialization as execution proof. These choices address the three reproduced merge-base review findings without adding publication authority or production wiring.

## Context and Orientation


Continue in the existing managed worktree named `teams-message-edit`, on `feature/teams-message-edit`. Its planning baseline is commit `ed59b5f52d66a3a1a78bd312bb62614b2d0a15f4`. The optional add-on lives in `packages/teams-graph-addon/`. `evander_teams_graph_addon/tools.py::create_teams_tools` registers the MCP calls, including `teams_post_file` and `teams_update_message`. MCP is the host tool interface used by agents; the gateway binds calls to the authenticated agent session. `commands.py::TeamsMessageCommands.update_message` enforces the shared authorization and audit boundary. `workflow.py` supplies the typed, bindable `effect:teams:update-message` provider, which calls that host command directly, without MCP transport or inference.

`service.py::GraphTeamsService` owns Graph requests. `_teams_file_message_payload` currently posts image bytes as hosted content when creating a new message. `_teams_message_url` builds encoded channel-root, channel-reply, and chat endpoints. `message_editing.py` captures the editable text span from an acknowledged post, verifies protected content, serializes edits per conversation and message, persists pending edits, PATCHes only the body, then reads back the result.

A receipt is durable evidence that a particular agent session posted a particular message in a particular conversation. `src/evander/teams_outbound.py` defines immutable `TeamsOutboundReceipt` plus mutable `TeamsOutboundEditState` and `TeamsPendingEdit`. `src/evander/repositories/records.py` stores receipts separately from refreshable incoming message records in SQLite and in a sibling JSON store for legacy storage. Duplicate message IDs in different conversations remain separate. `src/evander/integration_services/teams.py` defines the service contract and the no-network stub backend.

`src/evander/communication_artifacts.py::CommunicationArtifactStore` stages immutable bytes and metadata. `src/evander/communication_artifact_links.py` issues expiring signed download URLs. `src/evander/admin/web/artifacts.py::download_communication_artifact`, nested in `artifact_routes`, serves those bytes. Signed image URLs are bearer capabilities: never expose them in audit logs, test output, exception strings, or tracked examples. Graph must receive them to render the selected image. Keep their lifetime bounded and retain image bytes at least as long as the issued URL.

`src/evander/policy.py` already enforces file ownership, outbound file policy, target capability, and optional approval through `require_communication_file_artifacts` and `require_communication_file_send_approval`. `src/evander/gateway/communication_artifact_helpers.py` currently prepares artifact payloads and file links inside the gateway. Extract reusable publication logic rather than importing gateway closures into workflow providers.

An approved outline defines chapters and the required writing entries in each chapter. A completed chapter means all its required entries have verified successful results for the current job and current outline. A fragment file merely being present is insufficient. Drafting, editorial/style review, export, render verification, and delivery are different phases. Word and PDF are delivered only after separate successful receipts matching the current output hashes.

Validate the selected artifact bytes, checksum, PNG signature, dimensions, MIME, size, ownership, expiry, and approval before issuing a URL or contacting Graph. Use the existing configured retention and signing settings; do not silently lengthen global retention or return a source whose artifact expires sooner than its token.

Compose Markdown-like text and the one generated image paragraph, leaving every other protected token and collection unchanged. PATCH only `body`; never include `hostedContents`, `attachments`, `mentions`, reactions, or cards in an edit request. Compare the current Graph body, author, parent, and protected content against the last verified state before writing. Refuse ambiguous or external changes rather than adapting them silently.

Use a semantic operation identity containing text, selected image digest, slot action, and source identity. Repeating an identical successful update returns `unchanged` without a new URL or revision. Reuse the same image version for an unchanged snapshot while its source remains valid. Expiry renewal deliberately stages a new source artifact with the same PNG bytes and a new lifetime; that distinct source identity is a new edit intent even though the pixels are unchanged. ## Idempotence and Recovery


A receipt is created once and never rewritten to change ownership. Edit state may advance only under the existing conversation/message lock after readback verifies the intended update. No-op identity uses text and image semantics, not a newly minted signed token. Preserve old state and pending intent across process death. A different request cannot overtake an unresolved intent or a newer workflow snapshot. A renewal uses a durable source-version identity, and delayed timers for a superseded source or terminal job are harmless no-ops. Ordinary unchanged snapshots do not suppress a due renewal.

Initial message creation has a separate durable intent because Graph POST lacks a reliable general idempotency guarantee. A lost response must stop automatic reposting; it does not authorize guessed ownership. Operator reconciliation is bounded to the explicit test/job and must not inspect or modify unrelated conversations. Progress reporting failure does not stop documentation production.

Image versions are immutable. Garbage collection may remove only unreferenced or expired media according to existing privacy and retention rules; never delete a version still referenced by a verified message or unresolved intent before its valid expiry. Clearing the managed image leaves protected content intact. Never roll back by restoring stale whole-message HTML or by reposting into the thread.

The rollout flag defaults off. New code must preserve old workflows and text-only receipts. If a future rollout is disabled, stop new progress work, let documentation continue, and retain readable status; do not interrupt or wake active agents. Any live pack rollback uses the current Admin revision and lock rules rather than restoring an old file directly.
